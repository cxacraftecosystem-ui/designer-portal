## 0. What this is, and what it deliberately is not

The request was *"a scalability, ergonomics, concurrency, and offline audit of the entire
application"*.

**It is not a re-run of [`docs/SCALABILITY.md`](SCALABILITY.md).** That document is 1,526 lines of
measured latency work and it stands. This one exists to say two things it cannot: **what has changed
under it since it was written** (§1), and **what it never covered at all** — concurrency,
offline-versus-online divergence between the two clients, and ergonomics (§3–§8). Where a subject is

**No new latency measurement was taken.** The brief forbids running the app's gates and I changed no
code; every number below is either a count of source facts (words, call sites, round trips a
function issues) or a figure quoted from SCALABILITY.md with its label intact. Nothing here is
labelled MEASURED unless SCALABILITY.md measured it.

### Severity ladder, applied strictly

| Rank | Meaning |
|---|---|
| **DATA LOSS** | Work a person did is destroyed, or cannot be committed and dies with the tab. |
| **CORRECTNESS** | The system stores or shows something untrue. Nothing is lost, but a reader is misled or a record is wrong. |

## 3. DATA LOSS

### A30-01 — A required picker whose list failed to load refuses the save

> **STATUS: OPEN IN PRODUCTION (`bf601bd`). CLOSED IN THE WORKING TREE**, by another lane, while this
> document was being drafted. Both halves of the remedy below were taken, including the one this
> finding warns is not optional. The finding is kept in full for three reasons: **the fix is
> uncommitted, so the shipped build still refuses the save**; the reasoning is what the eleven
> sibling forms in §5/A30-12 still need; and a register that quietly deletes an item the moment
> somebody touches it cannot be used to check whether the deploy actually carried the fix.
>
> **What landed** (`ProcessForm.tsx:626-627`, working tree):
>
> ```tsx
> const artisanRequired = artisanOptions.length > 0;
> const productRequired = artisanProducts.length > 0;
> ```
>
> …consumed at `:882` and `:886` under a comment naming *"R2b, and the `&& options.length > 0` half
> is the whole point of these two lines"* — **and, critically, also at `:1255` and `:1338` as
> `<Field label="Artisan" required={artisanRequired}>`.** That second use is R3: the label stops
> claiming the field is required in the same breath that the validator stops enforcing it, which is
> the half this finding says must not be skipped. It was not skipped.
>
> **To verify the fix reached production:** search for `artisanRequired` in the deployed bundle, not
> for a line number.

**Claim.** Offline, a designer cannot save a process at all, and the record plus every step
photograph attached to it is lost when the tab closes.

**Evidence**, as `bf601bd` shipped it —
`frontend/components/forms/ProcessForm.tsx:806-813` at that commit (`:882-889` in the working tree,
where the guard now stands):

```tsx
if (!artisanId) {
  setArtisanError("Please select an artisan");
  blocked = true;
}
if (!productId) {
  setProductError("Please select a product");
  blocked = true;
}
```

There is no `&& artisanOptions.length > 0`. `:831-836` then returns:

```tsx
if (blocked) {
  setError("Please fill the required fields highlighted above.");
  setGuardOpen(false);
  if (focusId) document.getElementById(focusId)?.focus();
  return;
}
```

and `saveOrQueue` — the call that banks the write into the IndexedDB outbox — is at **`:869`**,
thirty-three lines *below* that return. The artisan list is loaded at `:530-538`:

```tsx
listResource<Artisan>("/artisans", { pageSize: LIST_PAGE_CEILING })
  .then((result) => { … setArtisanListState("loaded"); })
  .catch(() => setArtisanListState("unavailable"));
```

Offline the `.catch` fires, `artisans` stays `[]`, the dropdown draws with no members, `artisanId`
stays `""`, and the guard above refuses. `productId` is worse: its list at `:602` is keyed off
`artisanId`, so it cannot populate even in principle.

**The failure.** A designer in a courtyard with no signal fills in a process, attaches step
photographs, presses Save, and is told to fill in a field the app never offered them. There is no
path past it. The outbox that exists precisely for this moment is never reached.

**This is fixed on Android**, with the incident written into the code.
`android/…/MainActivity.kt:10129-10130`:

```kotlin
if (artisans.isNotEmpty() && artisanId.isBlank()) artisanError = "Please select an artisan"
if (artisanProducts.isNotEmpty() && productId.isBlank()) productError = "Please select a product"
```

and the eight-line comment above it (`:10122-10128`) names the rule and the incident:

> R2 — A FIELD MAY ONLY BE MANDATORY WHERE IT IS ANSWERABLE. […] must not refuse the save the way a
> required closed list with no members did in the OFFLINE_STATES incident (`LocationFields`): native
> validation blocked the submit before the offline outbox was ever reached, and the interview and
> its photographs died with the tab.

The web is the client that incident is named after, and the web is the client still carrying it.

**Remedy** (this is what the working tree took). Two lines, matching Android exactly:

```tsx
if (artisanOptions.length > 0 && !artisanId) { … }
if (artisanProducts.length > 0 && !productId) { … }
```

**Do not reach for `artisanListState === "unavailable"` instead.** `ProcessForm.tsx:442` already
holds that state and `:570` hands it to `carryScope`, so it is tempting — but it is the wrong
predicate by one case. A *successful* fetch that returns zero rows (a researcher scoped to a
workshop with no artisans yet) is `"loaded"` and still has nothing to pick, and Android's
`isNotEmpty()` covers both. R2 is a rule about the control's contents, not about the network.

**Second half, and it is not optional.** R3 — the control must SAY which case it is in — is what
stops the two-line fix from silently accepting a process with no artisan. `CarryContextBanner.tsx`
already models the three states (`CarryScopeState = "pending" | "loaded" | "unavailable"`,
`:69`), and `carryScope` is already wired at `:570`. The sentence exists; it is the picker that does
not print it.

## 4. CORRECTNESS

### A30-02 — `POST /api/questionnaires` writes three tables with no transaction

**Claim.** A questionnaire created by hand is written as `1 + S + Q` separate awaited statements
with nothing wrapping them, so a request that dies part-way leaves a designer owning a truncated
instrument that no screen can distinguish from a complete one.

**Evidence.** `backend/app/api/routes/questionnaire_forms.py:938-970`. The `Questionnaire` row is
created at `:938`; the section loop creates one `QuestionnaireFormSection` per iteration at `:953`;
the nested loop creates one `QuestionnaireFormQuestion` per question at `:962`. No `db.tx()`, no
`create_many`, no batching. At SCALABILITY.md's MEASURED 694 ms per cross-region round trip, a
24-section instrument with 284 questions is `1 + 24 + 284 = 309` sequential trips ≈ **3.6 minutes**,
comfortably past CloudFront's origin timeout, and the client sees an error over a database that has
committed most of the work.

**This is the exact shape SCALABILITY.md §8.1 named**, and it survives *because* that section's own
example was fixed (§1.2 above) — the register moved on while a second instance sat in a different
file.

**And the answer is already written, sixty lines below it, in the same module.**
`app/services/questionnaire_forms.py:1004` and the essay at `:1049-1060`:

> **WHY A TRANSACTION.** This used to be a bare `create` followed by one `create` per section and one
> per question — up to 2200 sequential statements, none of them in a transaction […]. A request that
> timed out at question 900 of 2000 left the `Questionnaire` row and 900 questions COMMITTED,
> attached to the target workshop and owned by the caller, while the client showed an error: the
> designer retries, and now owns a truncated instrument next to a complete "(reused 2)" with nothing
> on any screen able to say which of the two is short.

That paragraph describes `create_questionnaire` as accurately as it describes the copy path it was
written for. `copy_question_set` was fixed; the create route it sits beside was not.

**Remedy.** Give `create_questionnaire` the shape `copy_question_set` already has: one `db.tx()`,
sections in one `create_many`, questions in one `create_many` keyed off the returned section ids.
Four round trips regardless of size. The bounds (`MAX_SECTIONS` / `MAX_QUESTIONS`) are already
defined in the same module and should govern both doors, not one.

**One trap for whoever takes it.** The section-code de-duplication at `:946-952` has a bug of its
own that a batch rewrite will expose: `codes` is only added to on the `else` branch, so a code that
*was* supplied and unique is recorded, but a code that was derived by `derive_section_code` is
**not** — two sections whose titles derive the same code therefore both take it, and
`@@unique([questionnaireId, code])` (schema.prisma:1471) refuses the second insert. Today that
surfaces as a 500 with the questionnaire row already committed. Inside a transaction it becomes a
clean rollback, which is better, but the de-dup should be fixed rather than have its blast radius
reduced.

### A30-03 — The web has no durable reference-option cache

> **STATUS: REMEDIATED 2026-09-03**, and it is a translation of the Kotlin exactly as the remedy
> below asked for rather than a new design. `frontend/lib/referenceCache.ts` now also holds the
> design-workshop stage pickers, under a disjoint four-segment `dw__<model>__<owner>` namespace in
> the same object store and at the same `DB_VERSION` — `owner` is the workshop id for WORKSHOP scope
> and `ALL` otherwise, mirroring `DwReferenceStore.cacheOwner`. Same no-expiry rule, and the same
> refusal to overwrite a populated cache with an empty answer. **What is deliberately still
> live-only**: searched, cascaded and by-id queries, exactly as on the handset — only un-searched,
> un-cascaded opens are written down. The models it will cache are a closed allow-list
> (`DW_CACHEABLE_REFERENCE_MODELS`) with a runtime narrowing beside it, because the models are the
> registry's and arrive as wire strings: a closed TypeScript union would fail *open* at the first
> cast. Neither grant model is on that list. See [DROPDOWN_DESIGN.md](../DROPDOWN_DESIGN.md).

**Claim.** Every design-workshop REF picker on the web is empty offline, and the web has nothing
equivalent to the store Android built for exactly this.

**Evidence.** `frontend/lib/designWorkshops.ts:1556-1567`:

```ts
export function listStageReferences(workshopId: string, query: DwReferenceQuery) {
  return apiFetch<DwReferencePayload>(`/design-workshops/${workshopId}/references${buildQuery({…})}`);
}
```

A bare `apiFetch`. No read-through cache, no fallback, no persistence. The web's IndexedDB schema
(`lib/designWorkshopStore.ts:710-720`) declares three stores — `STORE_DRAFTS`, `STORE_MEDIA`,
`STORE_REGISTRY` — and **no reference store**; `lib/offline.ts:243` declares the outbox and
`lib/questionnaireFormCache.ts:193` the form cache. Reference options are the one document in the
offline set that is never written down.

**Android solved this deliberately and wrote down why.**
`android/…/data/DwReferenceStore.kt:22-58`:

> A REF field is a foreign key. Before this, the renderer drew it as a text box holding the raw id
> […] because "a picker would need a per-model lookup that cannot be served offline". That reasoning
> was right about the constraint and wrong about the conclusion. […] every successful
> `GET /design-workshops/{id}/references` is written to `filesDir` under the key it was asked for,
> and every read is served from that file FIRST. **The network is a refresh, not a prerequisite.**

It even solves the harder half — ALL-scoped lists are keyed by model alone and shared across every
workshop on the device, so *"a designer who starts a brand-new workshop in a village — a workshop
with no server id at all, created offline, that could not possibly fetch anything — still gets the
artisan register that some earlier workshop on this same phone downloaded"*. And it states its
non-goal: *"No expiry. A stale artisan list is worth immeasurably more than no artisan list."*

**The failure.** A designer on a laptop with a dead tunnel opens stage 3, and the artisan picker is
empty. Combined with A30-01's shape this is not merely inconvenient — an empty required picker is
what refuses a save.

**Remedy.** Port `DwReferenceStore` to a fourth IndexedDB object store keyed the same way
(`model` for ALL scope, `workshopId:model` for WORKSHOP scope), read-through-first, no expiry,
`fetchedAt` recorded and shown. The argument, the cache key design and the non-goals are all already
written in the Kotlin file; this is a translation, not a design.

### A30-04 — Last-write-wins on a stage row, silently

> **STATUS: REMEDIATED 2026-09-03**, in the shape the remedy below specifies rather than the interim
> it offers. `DwStageEntry` gained `version Int @default(0)`
> (`backend/prisma/migrations/20260903090000_dw_stage_entry_version/`), the write is now
> `update_many(where={"id": …, "version": seen}, data={…, "version": {"increment": 1}})`, and a count
> of zero is read as a concurrent writer rather than as a missing row. The refusal is reported per
> row in the existing `errors` map under the reserved key `_row` and counted by `refusedAnswers`; the
> rest of the payload still saves. The response contract is written up in
> [DESIGN_WORKSHOP.md](DESIGN_WORKSHOP.md), and what is deliberately NOT guarded — the sweep and the
> workshop-header write — in [DATA_MODEL.md](DATA_MODEL.md).

**Claim.** Two designers with access to one workshop edit the same stage row; the second save
overwrites the first completely, and nothing on either screen says so.

**Evidence**, as the code stood at `bf601bd` — inside `write_everything`
(`backend/app/services/design_workshops.py`). *The line pin this paragraph carried was dropped on
2026-09-03 when the remedy moved the function; the quoted statement below is the evidence, per this
document's own rule that "a symbol survives the edit; a line number does not".*

```python
for row_id, data in updates:
    await tx.dwstageentry.update(where={"id": row_id}, data=data)
```

Addressed by primary key, with no `updatedAt` guard, no version column and no `WHERE updatedAt = ?`
predicate. There is no optimistic-lock column on `DwStageEntry` (schema.prisma:2921-3048).

**What is NOT the gap, and this matters for anyone taking it on.** The *insert* race is closed, and
closed well. `SINGLETON_CLIENT_KEY` (`:3848-3870`) writes a non-null sentinel so
`@@unique([designWorkshopId, entityKey, clientKey])` can refuse a duplicate singleton that Postgres'
NULL-distinct rule would otherwise have allowed, and the comment there describes the read-then-write
window in exactly these terms:

> `save_stage` reads the stage's rows, finds no singleton, and inserts one; that window is wide
> enough for a second designer on the same workshop — which `DesignWorkshopViewer` exists to allow —
> to do exactly the same.

*(Requoted 2026-09-03. That comment used to describe the window as "on a link where a round trip
measures 756 ms", and A30-04's remedy **removed the latency from the sentence rather than updating
it** when the database was co-located on 2026-09-02 — because quoting any latency there invites the
reading the guard exists to refuse: that a small window is an acceptable one. The gap is however many
statements `hydrate_entries` issues wide, whatever each costs, and two designers on one stage collide
inside it at any speed.)*

and the loser is then recovered rather than refused: `:4614-4615` re-runs the whole transaction after
`_absorb_key_collisions` rewrites the create as an update. That is a genuinely good piece of
engineering. **It converts the collision into an update — and the update is the unguarded one.**

**The failure.** Two designers on one workshop, both with the stage open, both typing. The second to
press Save wins every field, including the ones they never touched, because the payload carries the
whole entity. The first designer's answers are gone with no 409, no banner and no row in
`RecordRevision` for a stage entry.

**Remedy, in the order the constraint allows.** A `version Int @default(0)` on `DwStageEntry`, an
`updateMany(where={"id": row_id, "version": seen}, data={…, "version": {"increment": 1}})`, and a
count of zero read as the conflict. `db.tx()` already wraps the write, and `write_everything` is
already a re-runnable function *for this exact reason* (`:4566-4570`), so the retry machinery does
not need inventing. What does need deciding is the answer: the honest one is to return the server's
row alongside a 409 and let the client show both, which is more work than this finding can specify.
**A cheap interim that is strictly better than silence:** compare the row's `updatedAt` against the
one the client last read and put the mismatch into the existing `errors` map, which both clients
already render.

### A30-06 — The web outbox has no dangling-FK remedy and no unfile sentinel

**Claim.** Two failure modes Android detects, explains and offers a route out of are, on the web,

**Evidence.** `grep -c dangling frontend/lib/offline.ts` → **0**. There is no `unfiled` concept in

* **The unfile sentinel.** `Offline.kt:200-208, 302-305, 387-396`. `UNFILED_BY_CHOICE` versus

**Remedy.** Port `danglingField` and `unfiledLinkReason` — both are pure functions on Android

### A30-09 — `version` is published for an invalidation nobody performs

**Claim.** The API tells clients to cache on a version key. No client reads it.

**Evidence.** `backend/app/api/routes/reference.py:38-39`:

> The payload is a pure constant — no database read — so **a client should cache it and re-fetch only
> when `version` changes.**

`backend/app/services/address.py:1753` publishes `"version": 2`.

Neither client honours it:

* The web never reads `version` at all (`LocationFields.tsx` reads only the nested
  `districts.listVersion` as a passthrough default at `:107`, which is a different field and is not
  used for invalidation).
* Android caches, but `AddressReferenceCache.write` (`LocationFields.kt:310-316`) compares the

  overwrite-suppression and it is not version invalidation: it still costs the full fetch every
  time.

So the contract is stated in a docstring, implemented on the server, and honoured nowhere.

**The failure.** Not a data fault — a wasted round trip on every session, on the connection least
able to spare one, plus a docstring that misleads the next client author into thinking a mechanism
exists.

**Remedy.** Pick one and delete the other half. Either serve the payload with an `ETag` and let
both clients send `If-None-Match` (which is the same idea with no bespoke protocol, and which
SCALABILITY.md §9.1 already works through for the field registry), **or** strike the sentence from
the docstring. A conditional GET is worth roughly one 694 ms round trip per client session and is
the smaller change; do that.

### A30-10 — Upload size caps are enforced after the body is in RAM

> **STATUS: REMEDIATED 2026-09-03 — all four doors, verified one at a time.** The remedy is a single
> shared helper, `backend/app/services/uploads.py::read_upload_bounded`, which refuses on the
> declared `Content-Length` *before a byte moves* and counts the running total for the case where the
> header is absent or lying. All four call sites now read through it: `POST /media/measure`
> (`backend/app/api/routes/media.py`), `POST /design-workshops/ocr/identity` and
> `POST /design-workshops/{id}/dictate` (`backend/app/api/routes/design_workshops.py` — the two the
> table below calls "identity-card OCR" and "the second OCR door"), and
> `POST /api/questionnaires/upload` (`backend/app/api/routes/questionnaire_forms.py`, whose
> `_read_upload` now delegates rather than reading). One `await file.read()` survives in
> `backend/app/services/ai.py::transcribe_audio`, and it is **not** a fifth instance of this finding:
> its only caller is `POST /media/transcribe`, which is admin-only and whose body size that route's
> own docstring declares deliberately uncapped and unmeasured. The line pins in the table below were
> dropped when the fix moved them; the shape they describe is the evidence.

**Claim.** Four routes read the entire uploaded file into one contiguous `bytes` object and *then*
check whether it was allowed to be that big.

**Evidence**, as the code stood at `bf601bd` — all four followed the identical order:

| Route | Read | Cap checked |
|---|---|---|
| `POST /media/measure` | `media.py` — `content = await file.read()` | `if len(content) > MEASUREMENT_MAX_BYTES` |
| Identity-card OCR | `design_workshops.py` | `> settings.max_image_bytes` |
| The second OCR door | `design_workshops.py` | same shape |
| `POST /api/questionnaires/upload` | `questionnaire_forms.py` (`_read_upload`) | `> MAX_UPLOAD_BYTES` |

**The honest version of the risk, because the obvious statement overstates it.** Starlette's
`UploadFile` spools to a `SpooledTemporaryFile`, so the *receive* is bounded and a large body lands
on disk rather than in the heap. What is not bounded is `.read()`: it materialises the whole spooled
file as one contiguous `bytes`. So the peak is **one full copy of the body, at read time**, on a
1 GiB box running one uvicorn worker — the same box SCALABILITY.md §5 is written about, where a
668 MiB media object was the headline risk and `s3.download_to_temp` was built to stop exactly this
shape on the *download* side.

**The failure.** A caller posts a 400 MB file to `/media/measure`. They get a correct 413 — after
400 MB has been allocated. Two concurrent ones OOM the box. Note that the cap constants themselves
are small and sane; it is only their placement that is wrong.

**Remedy.** Check `Content-Length` before the read and refuse there, and read in a bounded loop with
a running total for the case where it is absent or lying. `services/memory_budget.py` already
derives a ceiling from `MemAvailable` and the cgroup's `memory.max - memory.current`, and
SCALABILITY.md §5.1 records that it *"only ever lowers a caller's constant, never raises it"* — so
the derivation this needs is written and in use; these four routes simply do not consult it.

## 8. Concurrency: the state of the whole backend, stated once

**There is no `SELECT … FOR UPDATE` and no advisory lock anywhere in `backend/app/`.** A repo-wide
search for `FOR UPDATE`, `pg_advisory` and `advisory_lock` returns nothing; every `query_raw` call
is a `SELECT 1` liveness probe or an analytics aggregate.

**There are exactly seven `db.tx()` sites**: `data_access.py:181`, `custom_sections.py:1865`,
`design_workshops.py:4554`, `design_workshop_access.py:954`, `design_workshop_grants.py:1452` and
`:1587`, `questionnaire_forms.py` (the copy path, `services/questionnaire_forms.py:1004`). Each
carries a written argument for why it needs one, and three of them cite `save_stage` as the
precedent.

**That is not, on its own, a defect.** Most write paths here are single-statement, and Prisma wraps
a single statement in its own transaction. The gaps are the multi-statement writes that were never
given one — A30-02 is the one I found, and the one instance of the exact shape three other files
have already fixed.

**Where locking is genuinely absent and it costs something**, in order:

1. **A30-04**, the unguarded stage-row `update`. Last-write-wins across two designers on one
   workshop, silently. The only one of these that destroys someone's typing.
2. **A30-05**, no idempotency key outside the stage family. A replay that crosses devices makes a
   second government record.
3. **The `upsert` create branch in `dictation_cap.spend`** — and this one is **correctly handled and
   is the model the rest should follow**, so it is not a finding. `dictation_cap.py:353-393` uses
   `{"increment": 1}` so *"THE ARITHMETIC IS POSTGRES', not this process's"*, and then states its own
   remaining race plainly: *"**The CREATE branch is not atomic.** An `upsert` is a read followed by
   an insert, so the first [concurrent pair may double-spend]. One increment, once per designer per
   day, on a shape that needs two microphones in the same [moment]"* — a bounded, argued, accepted
   race, with the cost named. **Every read-modify-write in this codebase should be held to that
   standard**, and A30-04 is the one that is not.

**Duplicate submission.** The web has three layers and no server layer: `committed`
(`ProcessForm.tsx:511`, *"ONE WRITE PER MOUNT"* at `:754`), the `SYNC_LOCK` Web Lock, and
`uploadedBatches` resumability. All three are client-side. The server accepts a second identical
`POST /processes` without complaint because nothing constrains it to refuse — A30-05.

**Android outbox replay is idempotent for the case it was built for and not beyond it.**
`PendingEntry.createdId` (`Offline.kt:111-116`) is described as *"the load-bearing one: non-null
means the record IS on the server, and re-sending [duplicates]"*, and `:852-855` confirms the create
leg — the 409 arm included — is wrapped in `if (entry.createdId == null)`. That is exact **for one
device's queue**. It carries no information a *second* device could use, which is A30-05 restated
from the client side.

**Queue-worker exclusion** uses `flock` (`main.py::_acquire_queue_worker_lock`). SCALABILITY.md §2
rank 7 already recommends a DB lease instead; a file lock is correct for one box and does not
survive the move to two, which is the shape KUBERNETES.md contemplates.
