Design Prototype Workshop · reconciling a 65-section specification with the code

What to build, what exists, and what not to touch

A 65-section product specification was written without a view of what is already implemented. Thirteen agents audited the repository domain by domain and resolved every requirement against the code, with citations. This is the reconciliation: 482 requirement items, and the seven places where building the spec literally would make the product worse.

Every verdict carries file:line evidence from code the auditor opened. Where a comment in the repository contradicted the code, the code won — two such stale comments are called out below, because both would have sent a planner in the wrong direction.

Read this before anything else

Seven traps: where the spec, followed literally, regresses the product

These are not stylistic disagreements. In each case the repository has already met the requirement by a different route, and in five of the seven the alternative route was chosen after the spec's approach failed — the failures are recorded in the code.

1

Rebuilding the QR payload as a deep link

§2, §45 — "QR should encode a share/deep-link URL."

The payload is deliberately not a URL. workshopCodes.ts:28-33: "A card printed at a workshop in 2026 has to scan in 2031, and a hostname is the part of a system most likely to have moved… a QR photographed on a table in a courtyard should do NOTHING in a general scanner app." The letters are stamped on physical tags with a five-year life and pinned across three trees by test_workshop_code_letters.py. Do instead: leave the payload alone and add App Links as a second, parallel entry surface for links shared over chat.

2

Inserting the Inspector tier and expecting authority

§26-27 — "Inspector/Reviewer sits above Designer, below Professor."

Design-workshop access is set membership, not rank: DESIGN_WORKSHOP_ROLES = frozenset({"DESIGNER","ADMIN","MASTER_ADMIN"}) (deps.py:135) guards eighteen routes. That is why Professor, at rank 40, cannot open a design workshop today. An Inspector at 37 would get zero workshop authority — and simultaneously, silently, gain the power to review and reject every Designer's records, because can_review_record is "strictly below me" and 35 < 37. The naive change does the opposite of the intent at both ends, and no test fails.

3

Building device-to-device record transfer

§3-4 — "Nearby / Wi-Fi Direct / Bluetooth transfer of a record."

The product has already answered "two designers, one courtyard, no signal" — and answered it by refusing to copy records between devices. entry_provenance.py:7-11 carries the owner's requirement verbatim: "a single canonical copy rather than a duplicate per designer", and the guide names the failure prevented: colleagues "scan a card to join THE SAME one, which is what stops a team ending the fortnight with four parallel workshops." Building Nearby transfer would manufacture exactly those parallel copies. The printed join card — a 110-bit secret scanned face to face, queued offline, flushed on reconnect — already solves the stated scenario.

4

Pre-gating AI controls on "is a provider configured"

§15 — "Disable the AI action when no provider exists."

Considered and rejected in writing, with the failure named (design_workshops.py:911-916): the probe is cached per tab, so a "no" "would survive an administrator pasting an API key: the microphone would stay hidden until every designer reloaded, with nothing on screen to say why." The shipped answer is a 503 at the moment it matters, naming the missing setting, not charging the daily allowance, printed verbatim by both clients. Building the pre-gate reintroduces the cached-"no" defect.

5

Adding a CONFLICT state to the workshop sync

§42-44 — "LOCAL_ONLY / PENDING_UPLOAD / SYNCING / SYNCED / CONFLICT / FAILED."

In the design-workshop path conflicts are prevented, not detected: field-level merge adds only what a device has never seen and never overwrites what a designer typed. A CONFLICT state requires the client to send a wholesale replacement so the server can detect divergence — which is precisely the behaviour that destroyed office-entered answers three separate documented times. The spec's six-state enum is also a regression: the shipped model distinguishes five kinds of "not synced" that a single FAILED would collapse. (A real conflict path does exist for the standalone record types and is already surfaced.)

6

Making task scope an access rule

§29 — "Assignments must respect scope."

Task scope here is descriptive and derivational: it generates the task's title and tells the accountability board what to count. It authorizes nothing, and db.assignedtask is read in exactly one backend file. The real gate is a different table, WorkshopAssignment. Making scope authoritative would duplicate that gate on a different key and break every task created without a scope — which the API still supports — turning "no task" into "no permission".

7

Adding Redis, a worker queue, and Nginx

§34-40 — the prescribed infrastructure.

A durable queue already exists with an atomic compare-and-swap claim, attempts/backoff, priority ordering and a covering index, drained by a dedicated systemd process. Two stale comments will actively mislead you: a k8s manifest claims "nothing in the queue claims a job atomically across processes" (false), and SCALABILITY.md claims the app/scale/ package is unreachable (false — all fourteen settings exist; it is dormant only because install_rate_limit is never called). Enabling rate limiting is a one-line change in create_app(), not a project.

The constraint that reorders everything

Android changes are not the same price as web changes

Every domain priced an Android gap as cheap and client-only. The release train makes that backwards. A backend migration is live within one push; the web within two; the handset only after somebody pushes a v* tag, the release is posted, and each device happens to come back into signal — on devices the product's own copy says are expected to run offline for a fortnight.

Two consequences the plan below obeys throughout: (a) effort estimates must be read in wall-clock delivery, not lines of code — an Android-only fix costs a tagged release plus fleet propagation; (b) any change the handset must understand has to be backward compatible on the wire, because a fortnight-old APK will be talking to the new server the whole time.

Phase 0 — three decisions only the owner can make

No code should be written against §26-30 or §3-4 until these are settled. Each one changes what gets built, not merely how.

  1. What may an Inspector actually do with a design workshop? Joining the frozenset makes it meaningless as "the people who sign the report". The alternative is a fifth scope system beside DesignWorkshopViewer — read-only, workshop-scoped. Recommendation: the fifth scope system. An inspector reviews; they do not run workshops.
  2. Name the tier INSPECTOR, not REVIEWER. "Review" already names a different, relational concept here — canReview is held by everyone at Field Contributor and above, meaning "may review anyone ranked below me". A role called REVIEWER makes that word mean two things at once. §26 explicitly permits an equivalent architecture; the UI label stays "Inspector / Reviewer".
  3. Is proximity transfer wanted at all, given the product deliberately keeps one canonical copy and the join card already covers the offline courtyard case? If the answer is yes, it is XL and needs its own design round for provenance and authorization-before-send. Recommendation: no — close the gap the spec was really pointing at, which is that the web has no join-card client at all.

The plan

Ordered by ripple, not by spec section. Everything in Phase 1 is independent and safe to start immediately. server web android all three

Phase 1 — no ripple, immediate

Config, one-line enables, and gaps with no shared-contract impact. None of these can break another client.
  • server Enable the rate limiter. Call install_rate_limit in create_app() and set the env vars. The package and all fourteen settings already exist. Closes §39 and the login-brute-force gap in one change.
  • web Disable the admin AI configuration UI (§17), leaving the implementation intact and the disabled state explained.
  • server Restrict BYOK to Designer and above (§16) and audit-log personal-key writes.
  • web Build the MultiEnumField ref branch. This blocks Phase 2's picker work — Android already renders a record-backed multi-select, the web does not, and adding ref_model to a registry field before this exists would render a required field as an empty closed list and make stages 13 and 16 permanently unsubmittable in the browser.
    LANDED 2026-09-03, and the block it named is lifted. FieldInput.tsx now dispatches on field.refModel into ReferenceMultiSelect, the mirror of Android's field.refModel.isNotBlank(). validate_registry enforces the declaration side: a MULTI_ENUM must name exactly one of an enum or a ref_model, never neither (which is the empty closed list this item warned about) and never both.
  • all three A machine-checked ladder-parity test, so a future tier cannot land on the server and be silently missing from five hand-kept Kotlin copies and the web mirror.
  • web android Edge auto-scroll during drag. The grips exist and work on both clients — what is missing is that a drag cannot reach a destination off-screen, which on a 360×640 phone means one position. This, not new handles, is the real §18.
  • android Dashboard card for Sketches & prototypes, plus the tile-registry parity check (§6).
  • server Correct the two stale comments that misstate the queue's atomicity and the scale package's reachability, before they cost somebody a rebuild.

Phase 2 — real gaps with a clear shape

Each closes a feature the backend or one client already ships. Highest value per unit of risk.
  • web The join-card / access-request client. The backend and Android ship this in full; the web has no client for it, and nobody can see the queue of requests Android is already filing. Add the request panel and the admin queue screen. This is the honest reading of §2-3.
  • all three Questionnaire sharing with access levels (§20), the "Questionnaire Utilized" field on the workshop record (§22) as a searchable selector, and smart default-selection (§23). Note the name collision the audit found: /questionnaire (singular, the global artisan instrument, already deterministically seeded) and /questionnaires (plural, designer-owned) are two different objects — §19-24 applies to the plural, §21's "default questionnaire" to the singular. Do not unify them.
  • server web Task assignment for Professor and the new Inspector (§29), plus tasks linked to the design-workshop record so a designer's assigned work reaches the surface they actually use.
  • all three Measurement provenance (§8) — one extra key in the existing fieldProvenance stamp, not the spec's new table. Both clients already hold method: "SCALE" | "RECTIFIED" at the propose button and drop it on the floor. A comment in measurement_provenance.py says this is impossible; it was true on 20 Aug and false three days later.
  • web android A media picker over design-workshop stage fields (§11) — the narrow, buildable version. The general "attach an existing file to a second record" cannot be built: MediaFile has exactly one parent and no join table, and two components have already fought and documented this.
  • server Registry declarations for the obvious free-text offenders — materials, tools used, stage-1 designer, the survey questionnaire link — after Phase 1's web ref branch lands.
    THREE OF FOUR ANSWERED 2026-09-03; the registry digest moved 29bbcc361b3e24c7 → 37b5ff5190ef0e63. Tools used is now a record-backed MULTI_ENUM over ToolDocumentation on both stages (processStep.toolsUsed, prototype.toolsUsed). The survey questionnaire link (§22) landed as surveyPlan.questionnaireRef — an additive REF: the required prose box beside it is untouched, and the picker is scoped by the asking ACCOUNT through ReferenceModel.viewer_where, which is what makes an ALL-scope picker safe over a per-owner table. Materials was judged and deliberately LEFT as TAGS, on two structural blockers rather than on effort: there is no Material model to back it, and a record-backed MULTI_ENUM is a closed list — this box and finalProduct.materials are both BASIC and required, so a workshop started from a designer's own brief would face a required field with no answerable option and could never submit stage 13 or 16. A prototype is also exactly where a designer records a material the cluster's baseline does not have.
    The wire-compat rule this establishes: a TAGS → MULTI_ENUM promotion changes no stored shape (both are a JSON array of strings), so it needs no migration; coerce_value skips the vocabulary check for a ref-backed field precisely so a fielded 0.0.7 APK's free text is still accepted; and every render surface prints an unresolvable non-id token verbatim. Follow it for the next promotion.

Phase 3 — structural, gated on Phase 0

Wide blast radius across all three clients. Each needs a design round before code.
  • all three The Inspector role, end to end — enum + additive migration, three ladder mirrors, the scope system chosen in Phase 0, and tests that fail rather than silently skip when a tier is added. The ladder edit is three lines; the scope decision is the work.
  • server Idempotency keys on the write endpoints the outbox replays (§53), and optimistic concurrency for the six standalone record types (§44) — not for the design-workshop path, where merge already prevents the conflict.
    §53 — LANDED 2026-09-03. A nullable clientKey with a plain @unique on Workshop, ProductDocumentation, ToolDocumentation and Process, minted at queue time by both outboxes over the same four-endpoint list. The replay contract is /media/complete's: a duplicate key returns the existing row through the same 201 and there is no replayed flag; another account's key answers 403. Artisan, QuestionnaireInterview and Craft were deliberately left alone — each already carries a unique constraint, and two idempotency mechanisms can disagree about what a duplicate is.
    §44 — SERVER HALF COMPLETE, AND THE SECTION IS NOT CLOSEABLE YET. An optional expectedUpdatedAt precondition is live on all six PATCH routes: None passes, a mismatch outside a one-second tolerance answers 409 with code: "record_changed", and the check runs inside the transaction and above the ledger write so a refusal takes the RecordRevision with it. It is inert. No client sends it, and the gap is mechanical and named: six Kotlin DTOs and six TypeScript types do not declare updatedAt — every one carries createdAt and stops — while the server has always sent it. Until a client deserialises the value it has nothing to echo back, so the two client halves are deferred rather than done.
  • server web Cross-stage carry-forward (§13). The audit names this the single largest source of hand re-entry in the product: reference hydration copies data at save time by design, but no internal cross-stage reference hydrates anything, so stage 16 cannot see the prototype's own materials and dimensions.
    PARTLY CLOSED 2026-09-03 — do not read it as done. hydrate_entries grew an internal path that resolves a REF against another DwStageEntry of the same workshop, and two mappings use it: finalProduct.prototypeRef (nine boxes, including materials and all three dimensions) and prototypeValidation.prototypeRef (three). The costs do NOT carry, and the reason is arithmetic rather than a refusal about the value — a prototype holds materialCost and labourCost, a final product holds one costPrice, and a mapping is one key to one key and cannot sum two heads; synthesising the sum would assert that cost is materials plus labour when stage 17 lists four more. The named unblock is costSheet.totalCost, which already declares derived_kind="SUM" over all six heads. Media never crosses on an internal carry, and thirteen other internal REFs are deliberately left un-hydrated, each argued by name in stage_schema.py's internal-carry section.
  • android Offline task read and queued status updates (§42), remembering the fortnight-offline fleet and wire compatibility.

Phase 4 — scale, measured rather than assumed

§33's 1,000 concurrent users is a claim to be tested, not a configuration to be installed.
  • Load-test first (§52) with a realistic mixed scenario, and find the actual bottleneck before changing architecture. The queue, the object storage, the health checks and the pooling already exist.
  • Offload report generation so a PDF/DOCX build cannot block a request or exceed the gateway timeout — the clearest genuine async candidate in the product.
  • Metrics and tracing (§49) — latency, error rate, saturation, queue depth and job age. Nothing exposes these at runtime today.
  • Index-backed text search and cursor pagination, replacing multi-column leading-wildcard scans on the paths that will feel it first.
  • Horizontal scaling — verify statelessness rather than assume it, and only then decide whether the ingress needs to change. Do not add Nginx without establishing what terminates TLS today.

What we will deliberately not build, and why

Recording these is as important as the plan itself: each will otherwise be re-proposed by the next reader of the spec.

  • Device-to-device record transfer over Nearby / Wi-Fi Direct / Bluetooth. Contradicts the single-canonical-copy requirement; the join card already covers the offline case. (≈5 XL items avoided.)
  • A URL-bearing QR payload. Would invalidate printed cards with a five-year physical life.
  • Pre-gated AI controls. Deliberately rejected; reintroduces a cached-"no" defect.
  • A CONFLICT state in the design-workshop sync. Would reopen three documented data-loss incidents.
  • Task scope as an authorization rule. Duplicates WorkshopAssignment and locks users out of work they can do today.
  • A second job queue. One exists, with atomic claiming; two stale comments say otherwise.
  • New drag handles. Both clients already render a 48dp grip with correct touch handling; the gap is auto-scroll.
  • A general cross-record media attachment. The data model has one parent per file and no join table.
