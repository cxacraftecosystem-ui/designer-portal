# UI/UX audit — 2026-10-16

The owner asked "see what else remains from a UI/UX perspective". This document is the answer for the
designer portal, on the web and on Android. It changes no code: every finding carries the fix it
proposes, and the fixes land on this branch (`feature/ux-fixes`) afterwards.

The documentation portal has its own audit at `documentation-portal/docs/UX_AUDIT_2026-10-16.md` on
its own `feature/ux-fixes` branch. Findings that are the same defect in both portals are marked
**[both]** here and there, so a fix can be made once and ported.

## Top issues

1. **DW-01** (P0, web): the "Design workshop visibility" type filter can never load. It asks the API for 200 workshops and the API refuses anything over 100.
2. **DA-01** (P0, Android): "Take photo" and "Record video" on every record form very likely crash when camera permission is missing.
3. **DA-03** (P0, Android): if the master admin's Settings screen fails to load, **Save settings** writes the defaults over the real configuration.
4. **DW-02** (P1, web) **[both]**: every `Field` with no `required` prop draws a red asterisk, so optional fields read as mandatory. One screen shows "Note back to them (optional) \*".
5. **DW-04** (P1, web) **[both]**: in dark mode the literal purple links, upload buttons and review row actions fall to 1.7–2.7:1 contrast. On the review queue the **Edit** button is close to invisible.
6. **DW-03** (P1, web): the new-artisan form says a workshop was "Filled in" while the box still reads "Select".
7. **DA-04 / DA-05** (P1, Android): about 65 places show raw "HTTP 404" text, inside one unstyled message line at the foot of a long page.
8. **DW-07** (P1, web): on a phone, the review queue and the design-workshop list are 900px tables, so status and the decision buttons sit off-screen.
9. **DW-06 / DA-09** (P1, both platforms): the review queue says in words that it cannot show the oldest records. That is a gap admission.
10. **DW-08** (P1, web) **[both]**: on a phone the core controls are 16–42px. That covers the hamburger, the back arrow, every `.field-button`, the row actions and the checkboxes.
11. **DW-10** (P1, web): the workshop overview shows two progress numbers that disagree, "5%" beside "9 of 22 stages complete".
12. **DA-06 / DA-07** (P1, Android): a failed load reads as "Fetching…" forever, or as "Nothing pending 🎉".
13. **DW-09** (P1, web) **[both]**: Gender on a new artisan is pre-set to "Male", so an untouched box saves a claim.
14. **DA-13 / DA-14 / DA-17** (P1, Android): legacy hard-coded colours make media rows unreadable in dark mode and the upload progress invisible in light mode.
15. **DA-25** (P1, Android) **[both]**: the shared text field sets no capitalisation and no IME action, so a phone types names in lower case and Enter does not move on.

## Web findings

### DW-01 · P0 · Workshop access → "Design workshop visibility" · Web

- **Status (2026-10-16):** **Fixed.** The type map pages through `GET /workshops` at the route's ceiling of 100 until the total is in hand (`DesignWorkshopViewersPanel.tsx`). `frontend/e2e/workshop-page-size-unit.spec.ts` holds every `/workshops` caller to 100 or less.

- **Screenshot:** `ux-shots.local/workshop-access_manage-1440.png`, `…-390.png`
- **Where:** `frontend/components/settings/DesignWorkshopViewersPanel.tsx:128` (`const WORKSHOP_PAGE = 200;`), used at `:337`. The sentence the reader then sees is at `:989`.
- **What:** the panel asks `GET /workshops?pageSize=200`. The route caps the page at 100 (`backend/app/api/routes/workshops.py:310`, `le=100`), so the request is answered 422 every time. The panel then prints "The workshop list could not be loaded, so the type filter is off. Every design workshop is offered." on every visit, for every admin.
- **Fix:**
  - Ask for `WORKSHOP_OPTION_PAGE_SIZE`, as every other `/workshops` caller does.
  - If the type filter truly needs every workshop, page through the list or have the server filter by `workshopKind`.
  - Add a unit test that every `pageSize` literal sent to `/workshops` is ≤ 100.

### DW-02 · P1 · Every form built on `Field` · Web **[both]**

- **Status (2026-10-16):** **Fixed at the source.** `RequiredMark`'s `when` is now mandatory and only a literal `true` draws the asterisk, so a `Field` with no `required` prop draws none. `frontend/e2e/required-mark-unit.spec.ts`.

- **Screenshots:**
  - `ux-shots.local/workshop-access_manage-1440.png` shows "NOTE BACK TO THEM (OPTIONAL) \*" and "NOTE (OPTIONAL) \*".
  - `ux-shots.local/artisans_new-390.png` shows Email, Phone, Gender and Status starred.
- **Where:** `frontend/components/ui/RequiredMark.tsx:48`, which is `function RequiredMark({ when = true })`. `frontend/components/FormControls.tsx:54` passes `when={required}`.
- **What:** `required` is `undefined` on any `Field` that does not set it, and a default parameter turns `undefined` into `true`. So all 96 `Field`s written without `required` draw the red asterisk. A researcher cannot tell which boxes are mandatory, and an artisan's email or phone looks compulsory. That invites invented values.
- **Fix:**
  - Change `Field` to `<RequiredMark when={required === true} />`, or change the default to `when = false` after auditing the call sites that rely on the bare `<RequiredMark />`.
  - Add a unit assertion that `Field label="x"` with no `required` renders no asterisk.

### DW-03 · P1 · New artisan / product / tool → Workshop picker · Web

- **Status (2026-10-16):** **Fixed.** The cause was `useRecordOffPage`: the read issued while the page was loading was cancelled when the page arrived, and the guard then refused to ask again, so the off-page workshop never resolved. The guard is now released when the read had not settled. The note is printed only while the box shows the workshop, and a prefill this account cannot read is withdrawn (`useRecordOffPageState`).

- **Screenshot:** `ux-shots.local/artisans_new-390.png`. The rendered text is in `artisans_new-1440.txt`.
- **Where:** `frontend/components/forms/DesignWorkshopSelect.tsx:376` sets the note. `prefillWorkshopId` runs at `:374`. The note's wording is `frontend/lib/designWorkshopDefault.ts:110`.
- **What:** the box reads "Select" while the sentence under it says "Filled in because it is the design workshop you most recently opened on 09/10/2026". The prefilled id is not among the first 80 rows, and the trigger does not draw the off-page record. Either the box is empty and the sentence is false, or the value is set and the trigger hides it. Either way the reader is told two things.
- **Fix:**
  - Print the note only once the trigger can show the workshop's title. Resolve it through `useRecordOffPage`, which already exists below, and pin it to the top of the options.
  - If the record cannot be resolved, clear the prefill rather than keep an invisible value.

### DW-04 · P1 · Dark mode: links, upload buttons, row actions, amber notes · Web **[both]**

## How this document is kept true

This audit is a **dated snapshot** of the tree at `c13bf5be`. Its `file:line` pins are the record of
that tree and are not re-pinned as the code moves (`docs/tools/check-docs.mjs` exempts this file from
its drift check, and still fails a pin that runs past the end of its file). What changed afterwards
is written under each finding as a dated **Status** line, and a status is never edited away: a later
change adds a later line.

| Claim | What checks it | What it cannot check |
|---|---|---|
| Every repository path and that every pin is inside its file | `node docs/tools/check-docs.mjs`, in CI on every push | Whether the line still holds what the finding describes |
| A finding marked fixed | The test named in its status, where there is one; the re-shot screens in `ux-shots.local/after/` (web) and `ux-shots.local/android-*.png` | Screens nobody re-shot, and any Android finding that was read off the code rather than run on a device |
| A finding marked skipped | The reason in its status | Whether the reason still holds — the work it waits on may have landed |
